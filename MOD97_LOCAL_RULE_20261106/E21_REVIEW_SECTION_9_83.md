### 9.83 E21: lives and births that survive a restart (11 November 2026)

An engineering job, with no experiment and no claim about learning (brief `OPUS_TASK_E21_RESUMABLE_LIVES_20261110.md`, branch `claude/e21-resumable-lives`, started from `40cb1c20`). `exp16_integrated.py` now writes `<receipt stem>.ckpt` at every scored stage of `life()` and every curve row of `develop17()`. Each holds the weights, the optimizer state, the torch RNG state, the receipt so far, the effective configuration, and a per-component digest of the data pipeline. The write is by temporary file, fsync and rename, keeps `.ckpt.prev`, and is sealed by its own sha256. With `E16_RESUME=1` a run replays the data stream with the learner off: every batch, admission and store write, but no update or evaluation. It then checks the configuration and the pipeline digest, loads the weights and continues. The receipt records each restart under `resumed`. This is exact because nothing in the data pipeline reads the weights; I checked that in the source and found no exception. `e21_resume_check.py` (results in `exp45/E21_RESUME_CHECK.json`, 4 vCPU Linux, Python 3.13.18, torch 2.15.0+cpu) ran 47 checks and all passed. For each of the brief's seven command shapes: this branch, not resuming, reproduced the base commit's receipts and final weights hashes exactly; and lives killed by SIGKILL before any checkpoint, inside a middle stage's updates, and inside a middle stage's evaluation resumed to the same scores, losses, weights hash and pipeline digests as uninterrupted runs. That held for one life killed twice and at 512 updates per stage for two shapes. A changed setting stops the run and names it; a damaged `.ckpt` falls back to `.ckpt.prev`; two damaged checkpoints or an edited digest stop the run; a kill inside a checkpoint write resumes from `.ckpt.prev`. Costs: a checkpoint is 9.6 MB (window net) or 13.6 MB (bank2) and takes 0.04-0.07 s to write; replay takes 1.6 s (window, with the store) or 0.3 s (bank2) of CPU per stage at 512 updates, which scales to an estimated 20 s and 4 s per stage at the full dose. Not covered: two processes writing one receipt; `exp11_cell.py` births, `exp19_kbank.py` and the summarizers; the other replay modes, which share the code but were not run; and resuming on a different machine or torch version, which is allowed and continues exactly from the checkpoint but need not equal what an uninterrupted run on the first machine would have given. The tests should be rerun on the owner's machine before merging (`python3 e21_resume_check.py`, about 2.5 hours on four cores).
