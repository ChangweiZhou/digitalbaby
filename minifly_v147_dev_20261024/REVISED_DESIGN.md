# V147-R1 — cycle revisions

The original V147 goal and constraints remain unchanged. This revision does not authorize extra training.

- Use uniquely named evaluator modules; the startup collision occurred before any learning and is preserved. Keep task code out of the kernel and restrict technical generators from opening H1–H4.
- Treat calibration as E1 acquisition, not an E3 verdict. Do not inspect holdback scores to rescue a failed naming-rate menu or lower the 95% gate retroactively. The gate is a scoped engineering criterion, not proof that poorer acquisition precludes all generalization.
- Freeze and learned-feature routes must both be considered. Inspect fixed-code collisions, teacher loss and final/birth code stability; poor fixed-code acquisition cannot be attributed solely to moving addresses.
- If acquisition remains unready, the next separately designed comparison should isolate encoding/readout convergence on identical fixed codes using permitted local rules. No exact-gradient reference, ELM solver, arithmetic feature, new task or automatic longer run is introduced here.
- Preserve own-byte/EOS scoring, gradual warmup, all record/token/cost accounting and a separately paid cross-process resume check. Keep the main assessment untouched until readiness and explicit authorization.
- Modular success, if later obtained, is only a diagnostic. Return to unseen ordinary addition with the same kernel/interface before any addition claim; starting fresh is an architecture test, not transfer of learned modular knowledge.

## What the completed calibration changes

Neither route reached the unchanged 95% taught acquisition gate in both worlds. At alpha 0.03, FIXED reached 66.91% and 77.54%, while LOCAL reached 44.44% and 44.93%. Thus do not spend the proposed 4,096-pass assessment budget or claim a failed generalization test: no held score was opened.

All examined FIXED codes stayed identical to birth, with no exact conflicting-target code groups. LOCAL codes changed substantially. LOCAL's average teacher bit loss was lower at the higher rate even though complete generated answers were worse. That makes average bit loss an inadequate readiness proxy. It does not identify whether payload decisions, EOS decisions, low margins, code overlap or nonstationarity is causal. Exact-code uniqueness also does not establish readout separability.

## Next comparison to specify before further learning

The saved-prediction reduction is complete: at alpha 0.03, LOCAL first-payload accuracy is only 44.69% / 45.41%, against 94.69% / 91.55% stopping after exactly one payload byte. FIXED first-payload accuracy is 68.60% / 78.74%. Focus the next comparison on payload naming/credit acquisition; an EOS-only fix cannot restore readiness. Preserve complete own-byte/EOS as the endpoint rather than replacing it with payload or bit accuracy. Any subsequently proposed learning comparison must be prospective and use fresh development identities.

The narrow candidate comparison is the unchanged fixed-code opponent readout versus one explicitly specified local output-credit alternative on identical generic byte traces and KC codes. Derive the alternative from the observed error category; do not assume a solver or introduce an ELM fit. Keep birth, record order, warmup, raw byte/EOS generation and total presentations paired. Include the original LOCAL arm to test whether any output improvement survives moving features. Change only one learning component; freeze the finite rates, dose, acquisition criterion and compute ceiling before fitting. Report complete answers and per-bit/margin diagnostics together, including all unsuccessful settings.

This is a proposal boundary, not an executable new experiment. A particular alternative and its numeric budget still need a separate design. No further fitting, longer practice, new curriculum or assessment is authorized by this revision. The ordinary-addition return test remains mandatory before an addition improvement claim.
