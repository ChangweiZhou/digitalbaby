**Verdict.** The network is the one the E49 audit asked for, and the specification file agrees with the brief's text. Seven changes are required before release. None alters the network or the three settings; one fixes the order of the runs, and one adds a measurement that can be computed from the committed weights.

The most important change corrects the paragraph headed "Time to travel". It says that any cell is within 3 connections of any other, and that a cell without input for the second operand's last digit cannot use it for the answer's first byte. Neither statement holds. The state of one cell reaches another within 3 connections for 83% of the ordered pairs of cells; the farthest pairs are 5 connections apart. A byte, however, starts in many cells at once: at the smallest setting a digit is read by 67 to 82 cells, and one position later it has reached 241 to 255 of the 256 cells. The second operand's last digit stands one position before `=`, where the answer's first byte is read, so at `=` nearly every cell can hold something of that digit. The forward itself confirms this count (section 2). What limits such a cell is the form in which the digit arrives: one number for each connection, the neighbour's state, and not the digit's code. A cell's ignorance of a byte therefore lasts one position, and the brief should say so.

The other required changes are these. The text does not give the digest's formula, the list of the 46 symbols or the formula of the entry's value. The reference inside the job (`C-dense`) is launched together with the settings that are read against it, and the brief has no rule for the case in which the reference itself does not learn, which the coordinator's own prediction puts at 45% under the sweep. Against `C-dense`, a masked setting can be read as needing *more* updates at the 80 threshold only if `C-dense` reaches that threshold by update 16,042, which under the sweep allows `C-dense` to be at most 6% slower than E42's `F10`. No figure of multiply-adds a position is given for any setting, and E49's counting function would still count `l1`, which is not computed in this job. The diagnostic "by what a cell knows" measures the size of weights and has no baseline; it does not show whether cells use what arrives through their neighbours, and a test that does is defined here and implemented in the reader. A shortfall of the smallest setting would have two possible causes that the job does not separate, and the brief should state both.

**Terms.**

- The *code* of a byte is the 512 values that feed the input map and `l2`. In E42 and E49 it is `z1 = tanh(l1(book[byte]))`, learned. In E50 it is fixed: a *used* byte turns on 11 values of its own, each equal to one number (the *value of a turned-on entry*, 3.2387 for seed 73129), and every other value is zero.
- The *used bytes* are the 46 bytes the first family puts into the network: the ten digits, the operation signs `+ - > <`, `=`, the 26 capital letters, the task codes `p q v w`, and the start symbol (257). The task must tell 20 of them apart (all but the letters). The letters stand between the operands and carry no information.
- The *input map* is `rnn.weight_ih_l0`, of 768 rows (three gates for each of the 256 cells) and 512 columns. `lm` (512 rows, 256 columns) carries the cells' states to the 512 *readout units*; the readout is `z2 = tanh(l2 z1 + lm h)`, and `l3` gives the 257 logits.
- *K_IN* is the number of values of the code a cell reads and *K_OUT* the number of cells a readout unit reads. The settings are `C-dense` (512, 256), `C64` (64, 32), `C16` (16, 8) and the conditional `C16-in` (16, 256). A cell *has input for* a byte if it reads at least one of the byte's 11 values.
- A byte or a cell's state is *within s connections* of a cell if it can affect that cell's state s positions later, through the 10 cells each cell reads (E42's connections) and the cell's own previous value.
- *A* and *R* are E42's scores on untaught pairs at 12 letters and on untaught reduction pairs without letters. The *sweep* is the sign rule; *backpropagation* is the exact gradient. A threshold is *reached* at the first of three consecutive scored rows at or above it, so the last update at which it can be recorded is 24,064.

## 1. The code, rebuilt from the text

**What the text says, and what the reader builds** (`e50_code_reader.py`, classes `Code` and functions `drives`, `forward`).

- *Which bytes have values:* the 46 used bytes. *How many:* 11 values each, 506 of the 512 values; 6 values have no owner. *Fixed or learned:* fixed; the list of the 512 values is shuffled once by `Random(f"e50|code|{seed}")`, and symbol number k (from 0, in increasing order of byte, the start symbol last) takes `vals[11k : 11k + 11]`. Every other byte, the end symbol among them, has the zero code.
- *What replaces the byte table and `l1`:* a look-up in this fixed table. The byte table and `l1` remain in the network object and take no part.
- *What `l2` now reads:* the fixed code of the present byte, all 512 values, of which 11 are not zero. A readout unit's input from the byte is therefore 3.2387 times the sum of its 11 weights on the byte's values, plus its bias. In the same way a cell's input from the byte is 3.2387 times the sum of its weights on those of the byte's 11 values that it reads. The input map and `l2` amount to two learned tables, one number for each pair of a byte and a gate of a cell, and one for each pair of a byte and a readout unit. The reader computes them in this form and never forms the 512 values, so it shares no structure with the specification file, which multiplies a table row by masked matrices.

**Does the job test the user's statement in the second sense? Yes, for a cell's direct input.** The E49 audit separated two senses: that a cell is connected to a small part of the input, and that the part a cell reads does not tell it which byte is present. In E49 the second failed, because any 16 values of the learned code identify the byte. In E50, when the present byte is one of which a cell reads no value, the cell's input is its bias alone. That input is the same for every such byte, for a letter the cell does not read and for the end symbol. At `C16` this is the case for a median of 14 of the 20 needed bytes and 7 of the ten digits. Such a cell cannot tell these bytes apart from its input, and the code is fixed, so training cannot change this.

A cell's ignorance of a byte therefore lasts one position. One position after a byte, the median cell at `C16` is within one connection of a reader of every needed byte. What it receives is not the byte's code. It is the states of its 10 neighbours, one number each, and each of those numbers also carries everything else the neighbour holds. Whether cells learn to recover what they need from that is the question `C16` asks, and it is a real one. The job does not test a network in which most cells stay without a byte for longer.

**The brief's paragraph "Time to travel" is wrong in two statements** (`python3 -I $C C`; required change 2).

- *"Any cell is within 3 connections of any other."* For seed 73129 the state of one cell reaches another within 1 connection for 3.9% of the 65,280 ordered pairs, within 2 for 28.6%, within 3 for 83.2% and within 4 for all but 28 pairs; the farthest pairs are 5 apart. No cell is reached by every other cell within 3. The other two seeds give 83.8% and 83.2%. The grid makes 3 the least possible for the farthest pairs, since two cells can be 8 rows apart and a connection covers at most 3; with 10 sources drawn from 48 it is not attained for one pair in six. The conclusion the brief draws, that a byte reaches every cell in 3 steps, is true and understates the case: a byte starts in at least 64 cells and has reached every cell after 2 positions.
- *"The second operand's last digit stands one step before the answer's first byte; a cell without input for that digit cannot use it for that byte, which only the cells that read it can supply."* The digit stands at the position before `=`, and the answer's first byte is read at `=`. A cell's state at `=` is computed from its sources' states at the digit's position, and a source that reads the digit holds it there. So every cell with a reader among its sources can use the digit at `=`: 241 to 255 of the 256 cells. The forward confirms the count. On the starting network of seed 73129 the last digit was changed in 3,600 items (40 for each ordered pair of two digits), and the cells whose state differs between the two runs were counted. At `C16` they are 113 to 137 at the digit's own position (the cells that read either of the two digits), 255 or 256 at `=`, and 256 one position later; at `C64`, 233 to 248, then 256. In every one of the 90 cases at each setting the set of cells is exactly the set within 0, 1 and 2 connections of a reader.

No failure on the answer's first byte in particular follows from the connections. The first byte also depends on the last digit only through a carry, while the second byte depends on it directly and is read one position later, when every cell is within reach. Scoring the two answer bytes apart is still a useful description; the stated reason for expecting the first to fail should go.

## 3. The reference

**It is the right reference, and it is in the roster.** `C-dense` is the same fixed code with both masks full: every cell reads every value and every readout unit every cell. Changing the code is itself a change, so the masked settings are read against `C-dense` and `C-dense` against E42's `F10`. The brief says both.

**It is not run first.** The brief launches six runs together. The masked settings can be read only against `C-dense`, and the brief gives no rule for the case in which `C-dense` does not learn. The coordinator's own prediction P50.3 puts the chance that `C-dense` reaches 80 on R under the sweep at 55%. In the other 45% of cases, as the coordinator estimates them, the two masked runs under the sweep would have no threshold to be read against, and the levels would be compared between runs none of which has learned. With a reference at a low level, the rule "*lower* at 15 points or more" would call a masked run that learned nothing "about the same". Required change 3 puts `C-dense` first and fixes what is said in that case. The cost of the order is nothing: with at most three processes the six runs take two rounds in any case.

**What a cost of `C-dense` against `F10` could be attributed to.** Not to sparseness alone. `C-dense` differs from `F10` in four things: the code is not learned, so nothing below the input map adapts; a value stands for one byte; every byte has the same length; and one update can move a cell's input for a byte by 0.0356, where in `F10` it can move it by between 0.0106 and 0.2049 (the first if the steps of the 512 weights were unrelated to the byte, the second if all helped it; `python3 -I $C D`). If `C-dense` costs much, the statement the job licenses is that this fixed code, at this value of a turned-on entry, costs; which of the four is responsible would need a further arm, and the brief should not name one.

**What `C-dense` against `F10` can show** (`python3 -I $C F`; `git show $W:$M/exp45/e42/e42_F10_<S|B>_73129.json`). `F10` reaches 80 on A at 13,312 (sweep) and 8,704 (backpropagation) updates and on R at 15,104 and 9,472. `C-dense` is *fewer* below 8,875 and 5,803 on A and below 10,069 and 6,315 on R; it is *more* above 19,968 and 13,056 on A and above 22,656 and 14,208 on R; and if it does not reach 80 it is *more* in all four cases, since 24,064 divided by `F10`'s figure is at least 1.59. The reading of the reference against `F10` can be computed in every case.

## 4. The start and the scale

**The sizes at the start are those of the reference** (`python3 -I $C D`; the starting network of seed 73129, first batch, positions of the items only). Root mean squares:

| | Input drive | Share of its entries exactly zero | Recurrent drive | A state | `l2`'s drive | `lm`'s drive | A logit |
|---|---|---|---|---|---|---|---|
| E42's `F10` (learned code) | 0.381 | 0% | 0.124 | 0.223 | 0.271 | 0.130 | 0.167 |
| `C-dense` | 0.389 | 0% | 0.118 | 0.212 | 0.276 | 0.123 | 0.165 |

- **The value of a turned-on entry does what it was chosen for.** The input drive and `l2`'s drive of `C-dense` are within 2% of `F10`'s. E49's factors √(512 / K_IN) and √(256 / K_OUT) keep the mean square of the input drive and of `lm`'s drive at the masked settings.
- **The readout units keep a comparable drive from the code.** `l2` is not masked, so its drive is 0.276 at every setting, against 0.271 in `F10`.
- **At `C16` the same mean square is distributed differently.** 71% of the entries of the input drive are exactly zero, and the others are larger: a cell's input for a needed byte has a root mean square of 0.654 when the cell reads one of the byte's values, 0.919 for two and 1.111 for three, against 0.389 in `C-dense` (at `C64`: 0.333, 0.463 and 0.585). These sizes are within the working range of the gates. A cell's own mean squared input drive over the batch varies between cells with a spread of 0.27 of the mean at `C16`, against 0.16 at `C64` and 0.14 at `C-dense`. The states are 9% smaller at `C16` than at `C-dense`. None of this is a defect of the start.
- **The sign rule's scale on the masked input map is not used in this job.** The code has no gradient, so no error is carried back through the input map or through `l2`. `MaskedSign` and `SignLinear` use the signs and their scale only for that backward step; the gradient of the map's own weights is the exact outer product (`git show $D:$K/e42_cells_spec.py`, class `MaskedSign`; `git show $D:$M/exp3_state.py`, class `SignLinear`). Under the sweep the sign rule therefore acts on the recurrent map, on `lm` and on `l3` only. In E49 it also acts on the input map, `l2` and `l1`. The two rules are closer to each other in E50 than in E49, and the brief, which says "the two rules are E49's", should say so (required change 7). The scale on `lm`'s mask and on the recurrent map is E49's and E42's.
- **How far one update can move a cell's input for a byte.** In `C-dense` it rests on 11 weights and one update can move it by 0.0356, which is 9.2% of its size at the start. At `C16` it rests on one weight in most cases; that weight starts 5.66 times larger than a dense one and moves at the same rate, so one update moves the input by 0.0032, which is 0.49% of its size, 19 times less than in `C-dense` (0.98% at `C64`). E49 has a difference of the same kind and states it in its section "What it cannot show". In E50 it has a consequence for what a shortfall of `C16` means (section 5).

## 5. The settings and the staging

**The three settings are reasonable.** They are E49's two masked settings and the dense one, on the same lists, so that E49's `I64` and `I16` are the same masks on the learned code. `C64` is a mild limit (a median cell has input for 16 of the 20 needed bytes and 8 of the ten digits) and `C16` a strong one (6 and 3). `C16-in`, run only if `C16` falls short, says whether the cost is at the input or at the readout, and the condition for it can be computed.

**A shortfall of `C16` would have two possible causes, which the job does not separate** (required change 7; recommendation a). At `C16` a cell has input for few bytes, which is what the job is about. At `C16` the input a cell does have for a byte also rests on one weight, larger at the start and 19 times slower to change in proportion (section 4). `C16-in` shares both properties with `C16`, so it does not separate them. If `C16` learns as `C-dense` does, nothing needs separating: the statement that a network learns although its cells have direct input for few bytes then stands. If `C16` falls short, the brief's forms allow only the description, and the report must not attribute the shortfall to what a cell knows. A setting in which every cell reads one value of every used byte (46 values a cell) would separate the two: such a cell has input for every byte, each through one weight.

**Staging.** The working rule asks for a full-length trial on one seed, with diagnostics, read before a roster. The whole job is one seed, and further seeds need a release, so the rule is followed in that sense. Within the job two things are missing.

- *The reference is not read before the settings that depend on it* (section 3; required change 3).
- *The job rests on E49's runner, which does not exist yet.* Review section 9.156 lists what is running: E41's two seeds, E42's other seeds, E46 and E47's trial. E49 is released and has no worker on the remote. E50's checks include E49's checks 3, 4 and 5 and omit E49's checks 1 and 2, which establish that the runner with both masks full is E42's `F10`. They are the base of this job and must have passed before it starts (required change 3).

**Should E50 wait for E49's result? No; it should wait for E49's runner and checks only.** E50 has its own reference, so its readings do not need E49's runs. E49's runs are needed for one comparison, which the report can make whenever both are on file: `I16` against `F10` is the cost of 16 values of a code that still identifies every byte, and `C16` against `C-dense` is the cost of 16 values of a code that does not. If E49's `I16` does not learn, a failure of `C16` adds little, and the report should say so. Run by E49's worker after E49, E50 also adds no line of work to those already open, which the working rule limits to three.

The last column is a different quantity. **What is saved is sufficient.** Starting and final weights with the code table and the masks allow the reader to recompute the scores and to run the test below. The dry runs of check 5 commit the same files after 256 updates, which lets the reader confirm the forward on weights that have moved before the dose is spent.

**The diagnostic "by what a cell knows" does not show use** (required change 6). It is the mean size, at the end of the run, of the recurrent weights into cells that have input for 0 to 2, for 3 or 4 and for 5 or more digits at `C16`. For seed 73129 the three groups hold 95, 131 and 30 cells (`python3 -I $C B`). Two things are missing. The size of weights is not use: a weight can be large and carry nothing the answer depends on. And there is no baseline: the figure at the start, and the same three groups of cells measured in `C-dense`, where the grouping means nothing, are needed to say whether a difference between the groups is more than chance.

**A test of use, implemented in the reader** (`e50_code_reader.patch_test`; mechanics in `python3 -I $C G`). Two items are run that differ only in the second operand's last digit. The first is then run again with, at the position of `=`, the states of chosen cells replaced by their states in the second run. If the cells that read neither digit are the ones replaced and the answer's first byte changes to the second run's, those cells carry the digit, and they can have received it only through their neighbours. On the starting network of seed 73129 at `C16`, with 200 pairs of items: replacing every cell gives the second run's logits exactly, replacing none gives the first run's; the cells that read neither digit (119 to 143 an item) have identical states in the two runs at the digit's own position and different ones at `=`; and before any learning, replacing only those cells moves a logit at `=` by 0.18 of the difference between the two runs (median over items), against 0.99 when only the cells that read one of the two digits are replaced. On a trained `C16` the same figures say whether the cells without input for the digit have come to carry it. The test needs nothing from the runner beyond the files already committed.

## 9. Recommendations (none holds the release)

a. **A setting that separates knowing few bytes from having one weight for a byte,** to be run with `C16-in` under the same condition. Each cell reads one value of every used byte, 46 values a cell, drawn from the byte's 11 by one generator `Random(f"e50|one|{seed}")` for cells 0 to 255 in turn and, within a cell, for the symbols in their order; the kept weights are scaled by √(512 / 46); the readout is dense. Such a cell has input for every byte, each through one weight, and its input drive has the reference's size (0.39). If this setting learns as `C-dense` does and `C16-in` does not, what a cell knows is what costs; if both fall short, the thin input is. The decision and the name are the coordinator's; the reviewer would check the draw's digest only.

b. **Check 4's tolerance.** Use 1e-5, or compare in float64. The reader's two forms differ by up to 3.3e-07 in float32 at the start, which leaves a factor of three under 1e-6.

c. **Check 3's scorer check.** State that E49's check 5 is run through E49's forward, since E26's births have a learned code, and that E50's forward enters the scorer in the same way. Add to the receipts whether the byte table and `l1` are bit-equal at the end to what they were at the start; if they remain in the optimizer and its decay reaches them, they shrink without any effect on the function, and the receipt should say which is the case.

d. **P50.7** scored on the mean of the last three scored rows.

e. **In the table "What a cell is left with",** add the figures of section 2 for one position later (needed bytes within one connection of a cell: 18 to 20, median 20; a digit has reached 241 to 255 cells), so that the table shows both what a cell lacks at a byte's position and how soon it can have it.

f. **For a later job, not this one.** K_IN counts values, so what a cell knows varies by chance from cell to cell (1 to 10 of the 20 needed bytes at `C16`). A draw that gives each cell all the values of a stated number of bytes would make the number of bytes known the setting itself. A single code shared by the 26 letters would leave more than half of a cell's input for the bytes that matter. And a network in which a byte reaches most cells only after several positions (fewer readers, or readers confined to one part of the grid, as in E47) would test ignorance that lasts.
