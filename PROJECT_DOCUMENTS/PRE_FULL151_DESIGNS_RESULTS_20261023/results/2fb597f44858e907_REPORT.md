## Post-hoc instrument check (not pre-registered; the verdict above stands)

The pre-specified decoder scored **below** the online readout of the same KCs: 0.48 against 0.71–0.74. So it cannot be an upper bound. I refitted it on world 211 using all 65,535 training slots (`posthoc_decoder.py`, `POSTHOC_DECODER.json`):

| Decoder setting | LAT4 held-out y | FE0 held-out y |
|---|---:|---:|
| as pre-specified (λ = 1e-4, 500 iterations) | 0.515 | 0.469 |
| λ = 1e-6, 3,000 iterations | 0.927 | 0.684 |
| λ = 0, 3,000 iterations | **0.982** | 0.609 (train 0.994: overfits) |

With a properly powered decoder, **LAT4's KC code supports reading the order-dependent target at 0.93–0.98**, above the 0.90 criterion. FE0's reaches at most 0.68. The pre-specified λ was too strong.

This is post-hoc, so it needs confirming on a fresh world with the decoder settings fixed in advance.

## Correction to iteration 1

Iteration 1 said that "even the ideal readout stays below the gate's 0.65, so fixing the learning rule alone would not be enough". That rested on this same underpowered decoder, and it is wrong:
- with learning rate 1.0, FE0's online readout alone reaches 0.59–0.61;
- a better decoder of FE0's KCs reaches 0.68.

The input-organ finding still holds. FE0 keeps the byte two back at only 0.22 at PN, where LAT4 keeps it at 1.00.

## Where this leaves the byte interface

With LAT4 (four PN latency classes, sensing only byte and time) → native PN→KC → plastic outputs, the fly's own route keeps two-byte order and learns to use it. It passes V9's full ORDER gate in 3 of 3 fresh worlds, with a 5-bit swap penalty.

**Still open:**
1. The interface criterion needs confirming on a fresh world with the decoder fixed in advance (for example λ = 1e-6).
2. Depth is limited to 4 bytes by design (88 PN, 4 latency classes).
3. Timing is fixed, so bytes arriving at irregular times are untested.
