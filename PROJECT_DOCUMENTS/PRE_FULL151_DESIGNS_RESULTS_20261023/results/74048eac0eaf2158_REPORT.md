# Hostile audit of the proposed byte-arithmetic warmup experiment

**Verdict: NO-GO for implementing or launching the proposed evolution experiment as written.** The warmup idea is reasonable. The design leaves the actual teacher path undefined, permits a cheap countermodel to satisfy its main Stage-1 numeric gate, and risks reusing a small task universe as if fresh seeds were independent sealed evidence. This audit did not change the prior design or V2 results and did not launch a learner run.

## Blocking findings

**P0 — The proposed byte-teacher event cannot pass through the current learner API.** [The design](../BYTE_ARITH_WARMUP_PREFLIGHT_20260926/DESIGN_NEXT.md) says the fly answers and then sees correct-answer bytes. But [`Full151ByteSensor.observe`](../BYTE_ARITH_EVOLUTION_V2/model.py) rejects any chunk not ending in `=` (line 176), while `V2Fly.choose` and `V2Fly.feedback` (lines 333 and 365) accept a question observation and then only a scalar grade. There is no post-answer byte-continuation method, preserved prediction eligibility for that continuation, or defined rule by which the observed answer alters persistent weights. The two prior supervised probes fit targets offline; neither tested this interface. A direct numeric-target loss may be a useful privileged control, but showing answer bytes as decoration around that loss would not establish byte-based teaching. **Fix:** specify the exact question/choice/answer-byte/update event sequence and byte delimiters, then unit-test it on a small learnable arbitrary mapping before testing arithmetic.

**P0 — The specified Stage-1 gate is not specific to learning four operations.** The design requires +10 percentage points exact over constant zero and no-prior teaching, positive gain on each operator, and no worse q90. I tested its proposed 384/128/64/128 split on eight deterministic **illustrative** worlds, not a confirmation sample. A deliberately weak countermodel stores warmup expression answers, uses a reversed operand pair when available (negating a stored subtraction answer), and otherwise predicts the most frequent warmup answer for that operator. It does **not** evaluate full arithmetic expressions. It scores **19.0% exact versus 7.7% for zero**, a **+11.2-point** gain, and improves q90 absolute error **55→44**. Its per-operator exact counts are `+` 24/256, `−` 10/256, `×` 124/256, `÷` 36/256; each exceeds constant zero on these rosters. A no-prior-teaching branch cannot learn its warmup table, though its inherited priors could reduce this measured gain; the countermodel is a demonstration that the current gate is not specific, **not a claim that the current fly can implement or pass it**. A learned symmetry rule would be legitimate narrow transfer, but the gate would not establish the intended arithmetic competence. See [AUDIT_METRICS.json](AUDIT_METRICS.json) and [audit_fixture.py](audit_fixture.py). **Fix:** report this countermodel and stronger part/answer-prior baselines; require prespecified per-operator floors and harder held-out operand/composition strata before promoting a model as a four-operation learner.

**P0 — The “sealed” set is used as a design decision and is therefore not sealed confirmation.** [DESIGN_NEXT.md](../BYTE_ARITH_WARMUP_PREFLIGHT_20260926/DESIGN_NEXT.md) lines 13 and 21 call 128 questions sealed while using their score to decide whether to alter the representation or launch evolution. Once read for that decision, they become development evidence. The Stage-1 generator has only **840** possible exactly balanced canonical expressions because division has **210**; the proposed life consumes 704. New random seeds reshuffle this finite pool; they do not create new mathematical instances outside it. A long population search can overfit repeated facts and answer priors even when each individual life has zero exact-string overlap. **Fix:** separate development, qualification, and one-use final confirmation, and include a structural held-out distribution or equivalence-class split that blocks reversed-pair and trivial-answer reuse. Do not call repeated qualification worlds sealed.

**P0 — “Locked five-band punishment” names the values but not the function.** [`benchmark.feedback`](../BYTE_ARITH_EVOLUTION_V1/benchmark.py) (line 210) and [`runner.grade_v2`](../BYTE_ARITH_EVOLUTION_V2/runner.py) (line 73) both output `0,−1,…,−5` but use very different error boundaries. For absolute error 16, V1 gives **−5** and V2 gives **−2**. Accidentally importing the wrong function could recreate V1's saturated teaching signal while appearing to obey the design. **Fix:** lock V2's exact bands (`0; 1–8; 9–24; 25–48; 49–96; ≥97`), import one named implementation, and test every boundary before any trial.

## Important nonblocking findings for a tiny interface pilot, blocking for evolution

**P1 — Preservation is confused with continued learning.** [The proposed gate](../BYTE_ARITH_WARMUP_PREFLIGHT_20260926/DESIGN_NEXT.md) asks grade-only continuation to retain the warmup gain relative to a frozen fork. A model that ignores all later punishment can pass that requirement. Measure two outcomes separately: retention of the warmup-acquired relation after later problems, and *incremental improvement caused by grade-only experience* on an appropriately held-out set. Neither can be inferred from a single shared test score.

**P1 — The teacher and selection schedules are underspecified.** The design does not state whether warmup gives a grade as well as an answer, the probability of answer reveal during withdrawal, the order and rule for raising expression length, or the minimum sample efficiency required. Its proposed +25% then +50% absolute thresholds are suggestions, not a frozen progression rule. Likewise “rank-ordered elites” does not specify population size, genotype fields, selection noise control, elite re-evaluation, mutation, or a stopping budget. This is enough for discussion, not a reproducible evolution runner. Retaining relative-best parents fixes V2's reseeding failure only if each parent is ranked on fresh matched development worlds and lineage IDs are actually checked.

**P1 — Attribution to MiniFly remains ambiguous.** The suggested trainable raw-byte route may carry all useful information while the Full151 KC path contributes none. An equal trainable-parameter control and input-route ablations are necessary. The inherited fixed Full151 bytes must still be accounted for separately. A success of a new engineered head cannot be reported as a success of the native Full151 value writer.

**P1 — The positive control validates the arithmetic fixture, not answer-byte learning.** A symbolic parser returning 100% only proves that answers are well-defined. Before arithmetic, require an online learning task where the answer-byte channel is necessary and the mapping changes per world, so a fixed prior cannot solve it. Test that target bytes are visible only after the first response, the resulting update persists to the next question, and read-only scoring changes no state.

**P2 — Runtime extrapolation is not an integrated benchmark.** The 4–6 seconds per GRU fit came from a standalone batched model without the proposed Full151+byte teaching loop, graded continuation, forks, and evolution bookkeeping. It is a useful warning against 131,072 new fits, not a trustworthy launch estimate. Time 8–32 *complete* individuals after the interface and scoring contract are fixed.

## Minimal repair order

1. Freeze a one-page causal interface contract: exact visible bytes, first choice, optional warmup answer, optional grade, update timing, expression-local reset, persistent state, and test-time read-only behavior. Add the V2 grade-boundary tests.
2. Implement only a tiny online teacher-channel positive control and a causal answer-byte versus same-bytes/no-write comparison. If it fails, stop before arithmetic search.
3. Build the Stage-1 fixture and explicit shortcut controls with development/qualification/final partitions. Preserve the original V2 benchmark as a separate named comparator. Predeclare a gate the symmetry-and-prior countermodel cannot pass.
4. Separate warmup acquisition, answer withdrawal, grade-only *new* learning, and retention under later problems. Fix the progression and population rules before a larger pilot.
5. Microbenchmark a complete 8–32-individual run; only then decide whether any evolution search is warranted.

The actual evidence level here is **E0 audit of interfaces, support, and countermodels**. No E3 arithmetic success or persistent learning core is claimed.
