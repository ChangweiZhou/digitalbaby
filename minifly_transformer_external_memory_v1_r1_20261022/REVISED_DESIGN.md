# V1-R1 postcycle design: bind content and stop state separately in the audit

The [prospective revision](DESIGN.md) and [three-cycle report](REPORT.md) replace the assumption that the Transformer host should be trained before testing native storage. Preserve the parent architecture, gradual native warmup, arbitrary byte values, target-free frozen key addresses and all causal/cost controls. No fixed-strength write policy is introduced.

The completed tests found content-specific native storage with imperfect bits and a poor EOS path. They used random PN inputs, not a trained byte encoder. Therefore the next stage is a bounded **actual learned-bridge** prototype, with the native baseline retained; the32-world evaluation remains unqualified. The following details must be implemented and locked before that prototype:

1. During training-only H0 calibration, log the complete same-slot cross-key and within-key cross-slot overlap matrices, activity, nearest collisions, and signed one-write cross-read influence matrix. Include passive branches and both target polarities. Keep geometry before H1 visible. No candidate addresses may be resampled or selected using targets. Generic byte copy/position losses remain trainable, not evidence that KC addresses separate.
2. Inspect payload and EOS margins, error dependence across bytes, score distributions on absent keys, all free outputs, every warmup strength and total sample/CPU cost. Use the original16-pass schedule as reference; a separately labeled64-pass development reference costs four times as many OLD presentations and is confounded with clock/dose. No unreported rate search.
3. H1 may learn to use signed noisy native responses; it must not receive targets, true length or membership on scored queries. A trained decoder could exploit information missed by raw sign thresholding. Run the oracle-fed codec and ZERO/FOREIGN lesions; a failure of direct thresholding alone is not proof the host is futile. If the actual bridge yields no target-specific information beyond N/SH, stop before spending the full H1 budget.
4. Test one separate **generic EOS calibration** arm, using only training-episode responses and variable-length payloads0–8. Learn a single scalar threshold/scale for the EOS response, with equal positive/negative class weight in its training loss; freeze it before development queries. Apply it at every position equally. This tests a readout bias, not a supplied value length. Keep the uncalibrated sign-threshold arm and report payload errors; a threshold cannot repair missing content. This is a proposed arm, **not implemented or tested** in the completed cycles. Its data/optimizer/CPU allowance must be charged inside H1, with an executable lock before execution; do not fit it on the three test seeds here.
5. Keep class-balanced EOS **teaching** as an alternative hypothesis, not another automatic arm. Reweighting native writes would change plasticity and requires separate design/authorization; calibration alone does not. Keep gradual pretraining and all original strength caps.
6. Once the learned bridge and host show a causal memory signal with correct byte/EOS serialization in bounded development, freeze the entire host/bridge and acquire fresh evaluation associations only through native writes. Report E1 attribution, practical table/DELTA comparison and all training overhead separately. No arithmetic/general-core adoption follows this track.

There is no new final roster, formal-run authorization or automatic launch. Retain the old addition track unchanged. The next implementation should resolve this small generic interface before a large hybrid campaign; do not claim an E3 result from E1 fact recall.
